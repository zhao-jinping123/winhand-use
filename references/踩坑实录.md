# 踩坑实录——为什么 Windows 版工具长这样

> 本文件记录 huashu-mac-use 移植到 Windows 的过程中真实踩过的坑。读它的价值不是背结论，是理解内核里每条规则对应的代价。**证伪旧结论优先于新增**——下面每条都标了实测环境，换环境先怀疑它。

## 一、PowerShell 5.1 的中文地狱（2026-09-07 实测）

**症状**：脚本里中文注释/字符串在 `powershell.exe` 下解析直接报 `Missing closing '}'` 或字符串截断，乱码成 `��`。

**根因**：PowerShell 5.1 对**无 BOM 的 UTF-8 文件按系统 ANSI（GBK）解析**，中文多字节把引号/括号吃掉。PowerShell 7（pwsh）默认 UTF-8 没这问题，但 pwsh 没有 .NET Framework 的 UIAutomationClient。

**规则**：`.ps1` 必须 UTF-8 **带 BOM**；`winuse.cs.inc` 读取时显式 `-Encoding UTF8`。改完文件用 python `utf-8-sig` 重写一遍（本项目 deploy 脚本会做）。另外**别再转出双 BOM**：先 `lstrip('\ufeff')` 再写。

## 一之补、缺 BOM 的脚本会被基准测试抓出来（2026-09-13 实测）

**症状**：`probe.cmd msedge` 直接报 `Unexpected token`，乱码成 `鎵句笉鍒板簲鐢`。基准的
`probe.matrix` 一度把 12/12 全部标成「可解析」——因为解析失败的错误输出里没有「找不到应用」，
按字符串判断就成了通过。**测试脚本本身也会骗人。**

**根因**：`probe.ps1` 是后来手工打的补丁文件，没有 UTF-8 BOM。中文注释/字符串在
PowerShell 5.1 下按 GBK 解析，整脚本语法错误。Win 内核 `win.ps1` 有 BOM 所以一直正常，
问题就藏在一个不常跑的命令入口里。

**规则**：

1. 仓库里所有 `.ps1` 必须 UTF-8 带 BOM；新增脚本先过 `scripts/check.ps1`。
2. 基准/测试脚本必须把「解析错误」当失败，不能只按关键词判断业务失败。
3. 回归测试要真的跑一遍命令入口（`probe.cmd` / `win.cmd`），只做静态检查不够。

## 二、Write-Output 污染返回值（2026-09-07 实测）

**症状**：`Resolve-Target` 找不到目标时先打印提示再 `return $null`，调用方 `if (-not $info)` 不生效，继续执行把 `$null.Hwnd` 传给 C#，报 `Cannot convert argument "hwnd" with value ""`。

**根因**：PowerShell 函数**所有输出都是返回值**。诊断文本 + `$null` = 数组，`-not` 数组恒为 false。

**规则**：被赋值调用的函数（`Resolve-Target`/`Convert-Coords`/`Invoke-FocusAction` 等）内部诊断一律 `Write-Host`，只有命令主输出用 `Write-Output`。这是 PowerShell 与 bash 最大的心智差异。

## 三、Add-Type 引用程序集：GAC 不在 Framework 目录（2026-09-07 实测）

**症状**：`-ReferencedAssemblies 'WindowsBase.dll'` 报「未能找到元数据文件」；`[Reflection.Assembly]::LoadWithPartialName('WindowsBase')` 返回 null。

**根因**：WPF/UIA 程序集物理位置在 `C:\Windows\Microsoft.NET\assembly\GAC_MSIL\…`（或 GAC_32/64），不在 `RuntimeEnvironment.GetRuntimeDirectory()`（那是 v4.0.30319 根目录，只有 System.* 在那里）。

**规则**：先 `Add-Type -AssemblyName WindowsBase, PresentationCore, PresentationFramework, UIAutomationClient, UIAutomationTypes` 加载，再用 `[System.Windows.Point].Assembly.Location` 这类**类型反查真实路径**做编译引用。另需 `System.Xaml.dll`（WPF 编译依赖 IQueryAmbient）。

## 四、DPI：GetWindowRect 的虚拟坐标 vs 截图物理像素（2026-09-07 实测）

**症状**：150% 缩放下窗口 rect 报 `1280×720`，`PrintWindow` 截图却是 `1920×1080`。坐标换算全偏。

**根因**：进程不声明 DPI 感知时，`GetWindowRect` 返回系统虚拟化的逻辑坐标；PrintWindow 的 DC 是物理像素。

**规则**：内核启动即 `SetProcessDPIAware()`；枚举窗口的 Rect 统一用 `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`（与截图同源），不用裸 `GetWindowRect`。

## 五、Win11 记事本是「多窗口单进程」+ stub 启动器（2026-09-07 实测）

**症状**：`Start-Process notepad` 后拿到的 pid 找不到窗口；新开的「无标题」窗口其实挂在**旧实例**的 pid 下（34532），启动器进程是短命 stub 已退出。

**教训**：Windows 上「启动 app → 拿 pid → 找窗口」这条链不可靠。规则：**按窗口标题找目标**（`win windows <标题特征>`），不要按「启动返回的进程」找。这也是 Resolve-Target 加「多窗口挑主窗口启发式」的原因——一个 pid 底下常躺着 GDI+ Window、Default IME、MSCTFIME UI、主机弹出窗口一堆隐藏窗。

## 六、新版记事本文档 UIA 只读（2026-09-07 实测）

WinUI3 记事本的 Document 控件 `ValuePattern.IsReadOnly=true`，`axset` 明确报 `fail:readonly`。这是**真只读**不是暗拒。写文本的出路：借焦点真实键入，或（更好）直接改文件再让 app 加载——「能不点就不点」。

## 七、UIA 摘要会把文件全文灌进上下文（2026-09-07 实测）

**症状**：`win ax` 一个记事本文档，`value` 字段直接输出 751 字符的 `.env.local` 全文（含密钥）。这在真实会话里等于把用户文件内容批量塞给模型。

**规则**：摘要输出中 `Document` 类型只报字符数，普通 value 截断 120 字符；需要全文用显式读回或截图。**工具输出也要做最小权限**。

## 八、PrintWindow 对最小化窗口必然失败（2026-09-07 实测）

最小化窗口 rect 落到 `-32000`，PrintWindow 返回零尺寸或黑图。`win shot` 会输出空图诊断而不是假装成功——「工具说成功不算数」对截图自己也适用。

## 九、switch 的 case 要 break（2026-09-07 实测）

PowerShell `switch` 匹配后**不自动跳出**，会继续测后续 case 直到 `default`。第一次写完命令表，每个命令跑完都追加一句「未知命令」。机械修复脚本本身还踩了「case 之间的注释被收进 body」和「双重 BOM」两个坑——修脚本的脚本也要测试。

## 十、来自 mac 版的移植注意（不是坑，是差异）

- macOS 有 `CGEventPostToPid` 后台投递；Windows 等价物是 PostMessage + UIA，可靠性分布完全不同，别照搬 mac 的经验值。
- macOS 的 `open -g` 后台启动；Windows 用 `Start-Process`，且注意 stub/多实例问题（见第五节）。
- macOS 有 `sharingType=.none` 让 HUD 对捕获隐身；Windows 没有对等 API，靠「窗口级 PrintWindow 不含 HUD」规避，桌面全屏取证要等 HUD 结束。
- Electron 的 CDP 在两端一致（cdp.js 原样复用，跨平台）。

## 十一、UIA 的 eN/path 必须全树语义，不能走「可编辑子树」（2026-09-07 实测）

**症状**：`win ax` 输出的 `eN`/`path` 基于全树，而第一版 `axset` 内部用「只含可编辑控件的子树」解析，两个序号体系不一致。窗口里只有一个输入框时碰巧对上（e0 都是第一个可编辑），两个输入框时 e1 会选错或落空。

**修法**：`UiSetValueSmart` 与 `UiInvokeSmart` 统一用全树解析（与 `win ax` 输出一致），SetValue 前再检查 `EditableLike`。用双输入框沙盒验证：`axset e1` 精确写入第二个框，第一个框保持空白。

**规则**：工具内部的所有引用体系必须与它输出的引用体系是同一个；「摘要列表」与「操作列表」用不同过滤条件时，编号立刻错位。

## 十二、退出码三态是给 agent 框架的契约，不是装饰（2026-09-07 补）

**症状**：第一版所有失败路径都 `exit 0`（PowerShell 默认）。Claude Code/Cursor 这类框架完全靠退出码判断工具成败：目标找不到也返回成功，agent 会拿着空结果继续往下走。

**修法**：全脚本统一三态——0 成功 / 1 失败（找不到 app、写失败、未知命令）/ 2 拒绝或未知（闸拒绝、跨桌面、借焦点失败、目标不存在）。`Resolve-Target` 失败自动置 2；`win doctor` 输出可作为框架侧验收。

## 十三、中间层 PowerShell 5.1 捕获输出必须先设 UTF-8（2026-09-07 实测）

**症状**：wrapper 脚本（PS5.1）调用 `win.ps1` 并捕获 stdout，中文首字符出现 `s`/`shi` 错位（`第二个框专用文本` 变成 `s第二个框专用文本`），而直接调用完全正常。

**根因**：win.ps1 按 UTF-8 输出，但中间 PS5.1 进程用默认 GBK 解码子进程 stdout。**注意这不是技能 bug，是调用方编码没对齐**。

**修法**：中间层先设 `[Console]::OutputEncoding=[Text.Encoding]::UTF8` 与 `$OutputEncoding`。已写进「多框架适配.md」坑清单。
