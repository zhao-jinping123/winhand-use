# 四层控制面详解（Windows 版）

**什么时候读这份**：probe 探出本地端口不知道怎么用、UIA 写入失败要判断该不该退层、要从截图坐标算能点的坐标、不确定某条输入路径失败怎么归因。

## L0 结构接口——默认起点

**1. 本地监听端口（Electron/CEF 类最值钱的通道）**

```powershell
Get-NetTCPConnection -OwningProcess <pid> -State Listen
curl.exe --noproxy "*" -m 3 "http://127.0.0.1:<port>/json/version"
```

返回里有 `webSocketDebuggerUrl` 就是 CDP——直接走 CDP，别碰坐标。开不了端口时带参重启：

```powershell
win open <app> --cdp 9333 --relaunch   # 内核追加 --remote-debugging-port=9333 --remote-allow-origins=*
```

⚠️ 两条 Windows 特有的坑：

- **WebView2 应用不吃命令行参数**。WebView2 的调试端口要设环境变量 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333` 后重启该 app。probe 若判出 Chromium 但 `--cdp` 起不来端口，多半是 WebView2，走这条路。
- **Chromium 藏在哪一层要实测**。Electron 渲染进程是同 exe 名的子进程（命令行带 `--type=renderer`），主进程的窗口可能是壳。probe 用进程表判，不看目录结构（mac 版被「顶层 Frameworks 为空」骗过一整轮，Windows 上等价坑是主 exe 旁边还躺着 `app.exe` 的多个实例）。
- 🔴 **本机跑着 Clash 类代理时**，curl 本机端口必须 `--noproxy "*"`，否则被代理吞掉误判「没开服务」。cdp.js 内部已设 NO_PROXY。

**2. app 自带 CLI/COM/自动化接口**（Blender `-b --python script.py`、Office COM `New-Object -ComObject Word.Application`、Electron 无 GUI 模式等）。最可靠的一层：原子、不抢焦点、不受 UI 状态影响。原则：**能走接口就不碰界面**，最后截窗口取证那一两步除外。

**3. URL scheme**：probe 从注册表反查（HKCU/HKLM `Software\Classes\<scheme>\shell\open\command` 指向该 exe）。注册了不等于能用，挖不动别耗。

**4. 配置文件/本地数据库**：有些状态直接读文件比操控界面便宜。**只读，不写**。

## L1 UIA 语义树——探到可用才走

Windows UI Automation 是系统级辅助功能树，读树、找控件、ValuePattern 写值**都不需要窗口在前台、不需要键盘焦点、不碰剪贴板、一次写整段**。

### 可用性分布（先验）

| 应用类型 | UIA 情况 |
|---|---|
| Win32 原生控件（Edit/Button/List 等） | 完整。ValuePattern 可靠 |
| WinUI3 / XAML Islands / 新记事本 | 完整，但 Document 控件常只读，SetValue 会被拒（IsReadOnly） |
| Electron/CEF | Chromium 接到 UIA 客户端请求后自动开 a11y；**但只有真正响应过的页面元素才入树**，树可能比 DOM 少 |
| Qt | 部分（5.9+ 有 UIA 插件，默认开）；自绘控件常断 |
| Java Swing/AWT | 需要 Java Access Bridge（`jabswitch` 启用），默认可能没有 |
| 自绘 Canvas / 游戏引擎 / 裸 WebView2 | 基本为空 |

### 唤醒与判据

1. `win ax <目标>` 纯读，无副作用。树空不要立刻判死：Electron/CEF 的树可能因页面未交互而延迟出现，**先点一下页面或等 1–2 秒再查**。
2. 可编辑控件 ≥1 → `win axset` 实写一段 → **读回 + 截图看状态指示器**。
3. 三种结果三种走法：

| `win axset` 结果 | 含义 | 怎么走 |
|---|---|---|
| `ok` 且读回一致、发送键变亮 | 真通 | **最优路线，全后台** |
| `ok` 且读回一致，但按钮仍灰 | 🔴 暗拒（控件自绘或 React 不认注入） | 退 L2 借焦点真实键入 |
| `fail:readonly / no-value-pattern` | 控件不支持 | 退 L2 |

暗拒是 Windows 上最常见的坑：`SetValue` 把字写进了控件视觉层，但应用自己的状态没更新（实测过 Web 技术栈输入框）。**读回一致不算通，状态指示器变了才算**。

### ref / 路径

`win ax` 输出每个元素两样东西：`eN`（本次会话的枚举序号）和 `path=0/1/2`（从窗口元素逐层 children 的索引路径）。**eN 换个命令就失效**；`path` 在窗口结构没变时跨命令可用（内核每次重新按路径解析）。元素路径比「按控件文案匹配」稳，但 app 小版本一更新照样断——断了就重新 `win ax`，不要猜。

## L2 窗口坐标——UIA 不可用时的主力

```
win see <目标>            # 截图 + 尺寸 + UIA 摘要一次拿
win op <目标> <x> <y> "文本" @截图.png    # 内核换算，你永远不做乘法
```

### 🔴 坐标系（Windows 上最容易错的地方）

窗口枚举和截图都走 **DWM 扩展边框矩形**（`DWMWA_EXTENDED_FRAME_BOUNDS`，含阴影，内核已统一），DPI 感知后返回的是**物理像素**。三套坐标：

| 坐标系 | 说明 |
|---|---|
| 窗口 rect 像素 | `win see`/`win windows` 输出的 rect；截图就是它的尺寸 |
| 截图像素 | 与窗口 rect 像素 1:1（无缩放，因为截图就是按该 rect 生成的） |
| 屏幕全局像素 | PostMessage 转 client / SendInput 用，内核内部换算 |

你从截图量的 `(x,y)` 直接传给 `win op`，内核算 client/screen。**每轮重新截图重新量**：窗口会被拖动、app 会改版。

四条坑：

1. **不设 DPI 感知时 `GetWindowRect` 返回缩放前的虚拟坐标**（150% 缩放下 1280×720 的窗口截图是 1920×1080），比例对不上就系统性偏移。内核启动时已 `SetProcessDPIAware`，别在脚本里自己关。
2. **`@图` 换算以图宽/窗口宽为比例**。降采样图同样适用（图是窗口的等比缩小）。
3. **最小化窗口的 rect 是 `(-32000,-32000)` 之类**，截图必然失败。先还原再截。
4. **窗口阴影/圆角**：DWM rect 含阴影，视觉内容四周有几像素透明边。点边缘控件先放大看图。

## 输入路径：Windows 上写文本的四种方式

| 路径 | 抢焦点 | 可靠性 | 备注 |
|---|---|---|---|
| L0（CLI/COM/CDP） | 否 | **最高** | 完全不碰事件系统 |
| `win axset`（UIA ValuePattern） | 否 | 高（原生控件） | contenteditable/Web 控件可能暗拒 |
| `win type --bg`（UIA 第一个可编辑） | 否 | 中 | 同 axset，自动挑控件 |
| `win type` 全局（SendInput `KEYEVENTF_UNICODE` 逐字） | 是（需前台） | 高 | 逐字符不依赖键盘布局，中文/emoji 都能打；分块间留 8–12ms |
| 剪贴板 + Ctrl+V | 是 | 中 | 🔴 破坏用户剪贴板，还还原不了图片/富文本；**别默认用** |
| PostMessage WM_CHAR/WM_SETTEXT | 否 | 低 | 只对原生控件有效，现代 UI 大多不认 |

`win type` 全局档实现的要点（已在内核）：`KEYEVENTF_UNICODE` 绕开键盘布局；utf-16 天然处理 emoji 代理对；发送完把时间戳记进尾迹文件，避免自己的合成输入被在场闸误判成「用户在动」。

## 后台点击（PostMessage）：机会性优化，不是主路径

`win op`/`win click` 先试 `PostMessage` 投 `WM_LBUTTONDOWN/UP`（不抢焦点、窗口被遮挡也行），截图差分验证。实测：

- Win32 原生按钮/编辑框：多数响应。
- 自绘 UI、Chromium 页面：**大概率不响应**（合成消息进不了消息泵的命中测试）。
- 差分≈0 就自动升级借焦点做真实点击，别在后台档上耗。

两条破除的迷信：

- PostMessage 后**必须留投递窗口**（内核已 sleep 80ms），发完立刻退出会丢事件。
- PostMessage 没有错误通道，返回 true 不等于生效——**差分验证是唯一判据**。

## 借焦点（降级档）：SetForegroundWindow 的现实

Windows 的前台锁比 macOS 严：`SetForegroundWindow` 只在调用进程是前台进程、收到最后输入、或目标线程被 attach 时才生效。内核做法：

1. `AttachThreadInput(当前线程, 前台线程/目标线程)` 后 `SetForegroundWindow` + `BringWindowToTop`；
2. 成功判据是 `GetForegroundWindow()==目标`，失败会重试一次并如实报 refused；
3. 用完**还原前台和鼠标位置**；
4. 借到焦点那半秒闪 HUD（四角橙色取景框），对窗口级截图不可见（PrintWindow 只画目标窗口）。

仍然会失败的场景：agent 跑在无交互会话、目标在另一个虚拟桌面、全屏独占游戏、锁屏/安全桌面。**这些不是 bug，如实报告**。

## 等 UI 就绪

轮询 + 超时 + 明确失败，不要固定 sleep：

- 等窗口出现：轮询 `win windows <关键词>`。
- 等「加载中」消失比等内容出现可靠。
- 像素差分轮询是兜底：同一窗口连拍三帧稳定视为就绪（**光标闪烁/动画的界面永远不稳定**，此时改看控件状态）。
- 模态对话框会让目标 app 的处理停摆，操作前先 `win ax` 读对话框文字。

> 同一段代码失败一次、成功两次的实录（mac 版同款教训，Windows 一样成立）：时序差异——清空文档后目标文本区还没真正拿到焦点就输入。固定 sleep + 假定成功不可靠，动作后必须回读。

## 性能

瓶颈从来是模型往返，不是截图（PrintWindow 单窗口几十毫秒）。优化方向是「少截几张、一次做完多步」，不是压缩截图耗时。
